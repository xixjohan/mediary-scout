# 手动触发能力盘点与订阅补搜统一方案

调查范围：当前工作区中可发现的订阅巡检、STRM 计划、媒体服务器刷新、活动重试、扩展调试、更新及 MCP 入口。代码存在未提交的订阅策略与多季改动；本文描述当前工作区，部署版本须另外核对提交指纹。盘点基于代码静态追踪，不声称覆盖所有隐藏入口，也没有实际触发网盘写入。

## 结论

最明确的缺口是已追踪的单部作品或单季没有面向用户的独立“立即补搜并按策略入库”入口。设置页已有全量“立即巡检”，它可能处理多部作品，不适合当作单条订阅操作。

另有一项比缺少按钮更严重的问题：MCP 的 triggerAcquisition 在校验 TMDB ID 后直接返回 triggered 和成功文案，代码没有调用入队或获取服务。调用者可能误以为任务正在执行，应优先消除这种虚假成功。本次为调查方案，未修改运行代码。

## 主流方案与现有依赖

- [Sonarr FAQ](https://wiki.servarr.com/sonarr/faq)：区分系统任务、作品、季及单集搜索，并允许从 Wanted 界面搜索缺失项；借鉴清晰执行范围和候选不合格原因。
- [MoviePilot 智能助手](https://wiki.movie-pilot.org/agent)：支持对指定订阅发起补搜；借鉴通过不同入口调用同一业务能力，而不是把助手返回文本当成真实受理。
- [Radarr FAQ](https://wiki.servarr.com/radarr/faq)：区分新增资源监测与手动搜索已有资源，便于用户理解为何需要补搜。
- [BullMQ 去重文档](https://docs.bullmq.io/guide/jobs/deduplication)：按键合并活动任务并返回已有任务可作为行为参考；其 Redis 架构不是本系统实现该功能的前提。

仓库已有 SQLite 工作流记录、reserveWorkflowRun 原子预留、队列消费者、活动和通知、按网盘并发、资源冷却与 115 写入保护。packages/workflow 已有 XState 和 acquisition-v2 的 run-state-machine；简单按钮状态可沿用现有组件，复杂执行状态优先复用现有模型。无须为此增加 Redis、BullMQ 或第二套调度系统。现有策略快照和多季改动处于未提交工作区，必须核对最终代码与迁移后才能视为可依赖基础设施。

## 合并实施方案

1. **统一业务命令**：提供服务端单目标补搜命令，输入当前用户、已授权的网盘、作品及可选季；服务端读取追踪状态和目录，按账号与网盘校验所有权，不能信任客户端提供的账号、CID 或策略。
2. **复用现有巡检核心**：把 worker.ts 中按单个追踪状态执行的逻辑提取为可复用用例，定时巡检、设置页全量操作和单项手动操作调用同一缺集计算、搜索策略、转存与校验链。不得以全局 force 扫描模拟单项补搜。
3. **明确入队与执行路径**：单目标补搜复用 `type3_monitor`，同时新增实际队列消费者；定时巡检仍按原有逻辑直接运行。只有确认消费者、按网盘并发和失败恢复都已接通后，才允许此类 run 进入队列。受理原子去重并返回真实 run ID；同一账号、网盘、作品、季与初始化、替换及恢复之间的锁冲突需覆盖，其他季在既有按网盘限流下独立。
4. **策略固定**：入队时保存实际策略快照和版本，后台执行只使用该快照；若现有未提交快照实现不支持单目标任务，先补齐再开放。手动入口默认补缺，不隐式洗版、覆盖或跳过范围约束。
5. **统一入口但保留不同语义**：订阅卡片/作品季行显示“立即搜索缺失资源”；活动页失败巡检提供“重新搜索本季”，创建新任务并关联旧任务，而不是重排无消费者的旧 run。设置页的“立即巡检”保留全量执行和成本提示。STRM 与媒体服务器继续使用各自已有操作，不强制改造成同一种任务模型。
6. **修复 MCP 真实受理**：将 triggerAcquisition 接到相同的单目标命令；验证 workflow:trigger 权限、账号及网盘归属，返回 queued、already_running、not_tracked、throttled 等真实结果及 run ID。对暂未支持的输入明确返回错误；未经入队不得返回 triggered。
7. **反馈与运营**：界面显示排队、运行、无缺集、无资源、完成或失败，并可进入活动详情；频率限制在服务端共享持久层原子实现。记录触发来源、目标、去重结果、耗时和策略版本，不记录凭据或完整敏感 CID。轮询只对活动任务启用，结束停止。

## 实施结果

- 新增服务端 `queueTrackedSubscriptionSearch` 与统一应用服务。服务端按账号/网盘重新读取追踪状态，只接受有效已追踪目标；上映状态和已播缺集均在入队前校验。`reserveWorkflowRun` 负责原子去重，并冻结当前订阅策略快照。
- 为排队的 `type3_monitor` 接入 worker 消费路径：电影走电影获取器，剧集/动漫走单季监测获取器；两者继续使用既有策略过滤、转存、验证与通知。定时全量巡检仍保留原有直接执行语义。
- 详情页为已追踪且有缺失内容的电影/季提供“立即搜索缺失资源”操作，显示忙碌/已受理状态并链接活动页。MCP `triggerAcquisition` 调用同一服务，返回真实 `queued` / `already_running` 或拒绝原因。
- 活动页失败的巡检任务不再重放旧策略快照，而是按当前策略创建新任务，并在新任务审计事件中保留来源 run ID；其他可重试任务继续走原重试语义。
- 内存与 SQLite 仓储的终态写入都会保留入队时的策略快照和手动触发来源，避免 runner 重建工作流记录时丢失不可变元数据。
- 验证结果：`npm run build:workflow`、`npm run typecheck`、手动触发/MCP/活动重试/双仓储契约定向测试（6 个测试文件、388 项）及定向 ESLint 均通过；Server Actions、获取编排、剧集状态保护、SQLite 双模一致性和样式令牌门禁均通过。

没有引入 BullMQ、Redis 或新状态机库：现有 SQLite 队列、原子预留、按网盘 claim、策略过滤器和工作流状态已经覆盖所需能力。当前只完成代码与文档实现，没有执行远程部署或生产网盘写入。

## 可行性、性能和边界

单目标执行避免全量扫描，数据库读取及一次原子预留成本较低；主要成本是索引器、AI 与网盘请求。连续点击按目标返回已有任务，冷却、并发限制及预算在服务端生效。客户端按钮禁用只能改善交互，不构成跨进程互斥。配置失效应直接给出修复提示，网络瞬态错误沿用有上限的退避。

Adapter 只负责网盘接口差异，策略组件负责硬过滤和排序，编排层拥有任务状态和幂等。任务状态采用现有生命周期；不把全量巡检、STRM 扫描和媒体库刷新硬塞进同一状态机或一套参数，因为它们的副作用和完成语义不同。

## 回归门禁

1. 单季/电影已追踪可入队；未追踪、跨账号、跨网盘及不合法目标拒绝。
2. 手动、定时和活动页重试同时触发同一目标时不重复执行；不同季与不同网盘按既有并发限制工作。
3. 入队后修改策略，运行仍使用固定快照；筛选、集数范围和搜索词与自动流程一致。
4. type3_monitor 只有在 worker 消费路径可用时才允许排队；活动页失败巡检创建可消费的新任务并关联来源，策略快照在完成后仍可读取。
5. MCP 不创建任务时不得返回成功；权限不足、无订阅、限流和入队失败都有可区分结果，成功返回真实 run ID。
6. 无缺集、未上映、无资源、配置错误、网络失败、成功及重启恢复均有明确状态；只有瞬态错误有限重试。
7. 115 范围内写入可用、范围外拒绝；不在测试中使用真实凭据或网盘写入。
8. 设置页全量巡检、单个 STRM 扫描和媒体服务器全库/局部刷新保持现有功能；验证并发与防误触反馈。
9. 浏览器验收桌面和窄屏的单作品/单季入口、忙碌态、重复点击、结果和活动跳转；不以页面加载代替真实任务受理验证。
