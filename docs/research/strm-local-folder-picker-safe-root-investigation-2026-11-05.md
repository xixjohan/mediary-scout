# 本地 STRM 目录选择器安全拦截调研（2026-11-05）

## 问题现象

在“可视化选择本地 STRM 存储目录”弹窗中点击推荐项“Docker 电影 (`/data/strm/movies`)”后，页面显示：

> 安全拦截：所请求的路径超出系统允许的安全浏览范围

## 根因与触发条件

前端 `LocalFolderPickerModal` 将 `/data/strm/movies` 作为预设路径直接请求 `GET /api/system/fs-browse?path=...`。接口的 `getAvailableRoots()` 在 Linux 上只纳入运行时 `fs.access` 可访问的固定候选目录：`/data`、`/media`、`/mnt`、`/strm`、`/volume1`，再加入应用 `cwd`。随后 `isPathAllowed()` 只按 `path.resolve` 的字符串前缀判断是否位于其中。

因此，若容器没有将宿主机目录挂载到容器 `/data`（或 `/data` 不存在/不可访问），它不会进入白名单，预设请求必然返回 403。此处“本地”指 Web 服务进程所在环境（Docker 时即容器文件系统），不是访问者的浏览器电脑。界面把示例预设呈现为可用位置，却没有先发现挂载或解释环境，形成产品契约不一致。

即使 `/data` 存在，当前检查也只是词法路径边界，不解析符号链接；这会让白名单内的 symlink 指向白名单外路径时绕过预期边界。`POST` 创建目录也采用同类词法检查，故安全修复必须覆盖浏览与创建两条路径。

## 复用现状与库调研

- **已有基础设施**：项目已实现 `GET/POST /api/system/fs-browse`、账号鉴权、只读演示模式限制、根路径发现、禁止目录过滤、写权限探测、目录创建及对应 Vitest 测试；前端已有 `LocalFolderPickerModal`、路径导航与推荐快捷项。STRM 输出任务本身使用服务端绝对路径。无需新增一套文件访问服务。
- **已有库**：该功能目前直接使用 Node `node:fs/promises` 与 `node:path`。根/路径判定是项目自有逻辑。依赖中没有专用的文件浏览器或通用目录选择库；`fast-glob`/`glob` 即便可用于匹配文件，也不能解决容器挂载发现、授权边界、符号链接逃逸或目录创建授权，因此不应拿它们替代安全策略。
- **成熟方案可借鉴**：
  - **Nextcloud Files**：以服务器端存储配置和用户权限为根，Web 客户端通过受控 API 浏览存储；可借鉴“仅展示服务已配置/授权存储”的边界，而不是把任意宿主机路径当作可浏览资源。
  - **File Browser**：部署方明确配置根目录（scope），所有文件操作限定在该根之下；可借鉴显式配置根、路径规范化和每次操作重新校验。
  - **容器化媒体服务（如 Jellyfin）**：通过 Docker bind mount 将宿主目录映射到容器可见路径，应用只处理容器路径。可借鉴把“容器内路径”说清楚，并提示运维配置挂载；宿主路径不会自动出现在容器内。

这些方案共同点是：文件浏览能力来自部署时明确暴露给服务的存储范围，路径浏览器不是宿主机任意文件系统的代理。新增前端文件浏览 UI 库不能代替后端隔离。

## 解决方案

### 建议方案：显式配置的 STRM 浏览根目录

1. 让部署配置明确声明允许浏览/写入的容器内根目录（例如 `STRM_BROWSE_ROOTS=/data/strm,/media`），并在容器编排中把目标宿主目录 bind mount 到对应容器路径。
2. 根目录解析为真实路径（`realpath`），不存在或不可访问的路径不进入可用列表；默认仅纳入应用专用数据目录或显式配置目录，避免把整个 `/` 开放给浏览器。
3. GET 浏览和 POST mkdir 共用同一个授权服务：先校验词法包含关系，再解析目标/最近存在祖先的真实路径，确认真实路径仍位于允许根下；拒绝 symlink 越界、路径穿越和根目录边界歧义。目录创建使用非递归或逐级受控创建并在创建后复核真实路径，避免 `recursive: true` 沿外部 symlink 创建。
4. 只有配置根下的路径用于“选择此目录”；示例快捷项仅在 API 返回根列表确实覆盖目标时启用。没有挂载时显示明确说明：“容器内未配置 `/data` 挂载；请在部署中挂载 STRM 目录，或手动填写服务可访问的容器路径”，不要伪装成可浏览的有效路径。
5. 对旧部署保持兼容迁移：首版保留当前存在的已知候选根作为默认值并提示迁移；新安装使用显式根配置。后续再考虑收紧默认值，避免无提示破坏既有实例。

不建议把 `/` 直接加入白名单：它虽能消除 403，却扩大到系统敏感目录，且当前过滤列表不足以构成安全边界。也不建议只增加 `/data/strm` 白名单：目录未挂载时仍无法浏览，且根目录配置仍隐含且难于部署排查。

## 同类安全门禁与避免回归

- **根覆盖门禁**：每个建议预设必须被服务器返回的某个有效根完整覆盖，否则 UI 显示不可用原因；不能只测 `path.resolve` 字符串前缀。
- **越界矩阵测试**：覆盖 `..` 路径穿越、根目录相似前缀（如 `/data2`）、编码路径、Windows 分隔符/盘符、无效或不存在根路径。
- **符号链接测试**：允许根内 symlink；拒绝根内 symlink 指向根外；对 GET 与 POST 各验证一次。
- **容器契约测试**：在开发/正式容器中验证配置的 bind mount 可见、可写性正确；缺失 mount 时 API 返回根列表和明确诊断，不把推荐项作为有效浏览结果。
- **授权测试**：GET 和 POST 均保持账号鉴权；演示模式 POST 仍拒绝；对未授权路径统一返回 403，不泄露根目录之外的文件存在性。
- **回归集成测试**：临时目录模拟“配置根/缺失根/根内子目录/逃逸 symlink”，调用真实路由验证响应；前端测试确认快捷项禁用说明及正常挂载下导航、选择、新建目录流程。
- **防漂移**：在现有 `/api/system/fs-browse` Vitest 路由测试基础上补充以上契约；必要时增加轻量静态门禁，检查默认预设与部署 mount/根配置同步。避免只断言错误字符串或只测试一个固定盘符。

## 结论

本次提示的直接原因通常是运行该 Web 服务的 Linux 容器没有 `/data` 挂载；深层问题是 UI 硬编码了路径预设，而 API 白名单按运行时存在目录独立生成。当前保护机制确实阻止了未授权路径访问，但反馈不够可操作，且词法边界未覆盖符号链接。优先复用现有路由与弹窗，改为显式存储根配置、同源授权校验和挂载状态驱动的 UI；不需要引入第三方目录浏览库。
